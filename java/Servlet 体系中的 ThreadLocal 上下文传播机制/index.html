    Servlet 体系中的 ThreadLocal 上下文传播机制¶

    在传统 Servlet 体系中，一个非常重要的设计思想是：

    一个 HTTP 请求通常由一个线程处理，因此很多上下文信息默认绑定在线程上。

    例如：

    • 当前请求信息
    • 当前登录用户
    • 当前事务
    • 日志 TraceId

    这些信息大量依赖 ThreadLocal 保存。

    这种设计在同步模型下非常简单、高效，但一旦进入异步、多线程场景，就会出现一个核心问题：

    请求生命周期 ≠ 线程生命周期

    线程发生切换后，原来的上下文可能就丢失了。

    1. Servlet 模型中的线程与请求关系¶

    传统 Servlet 请求流程：

    HTTP Request

        |
        v

Tomcat 工作线程 Thread-1

        |
        v

Controller

        |
        v

Service

        |
        v

DAO

    在同步调用中：

    Thread-1

 |
 +-- RequestContext
 |
 +-- SecurityContext
 |
 +-- Transaction
 |
 +-- TraceId

    所有代码都运行在同一个线程中。

    因此框架可以通过：

    ThreadLocal

    保存当前请求相关信息。

    2. ThreadLocal 为什么可以保存上下文？¶

    ThreadLocal 的结构：

    Thread

 |
 +-- ThreadLocalMap

        |
        +-- key=value

    也就是说：

    ThreadLocal 的数据属于线程，而不是属于请求。

    例如：

    Thread-1

ThreadLocal

{
    user="张三",
    traceId="abc123"
}

    只要代码仍然运行在 Thread-1：

    SecurityContextHolder.getContext();

    就能获取这些信息。

    3. Spring 中常见的 ThreadLocal 上下文¶

    3.1 Spring Security 用户上下文¶

    Spring Security：

    SecurityContextHolder

        |
        v

ThreadLocal

        |
        v

SecurityContext

        |
        v

Authentication

        |
        v

当前用户

    例如：

    Authentication authentication =
    SecurityContextHolder
        .getContext()
        .getAuthentication();

    可以直接获取当前登录用户。

    原因：

    用户信息已经绑定到了当前线程。

    3.2 RequestContext 请求上下文¶

    Spring：

    RequestContextHolder

    保存：

    HttpServletRequest
HttpServletResponse
Session
Locale
Cookie
Header

    例如：

    RequestAttributes attributes =
    RequestContextHolder.getRequestAttributes();

    业务代码无需层层传递：

    request -> controller -> service

    即可访问请求信息。

    3.3 Spring 事务上下文¶

    Spring 事务：

    @Transactional
public void save(){

}

    底层：

    TransactionSynchronizationManager

        |
        v

ThreadLocal

        |
        v

数据库连接 Connection
事务状态
资源绑定

    所以 DAO 层不需要手动传 Connection。

    因为：

    Thread-1

事务开启

ThreadLocal
 |
 +-- Connection


DAO

从 ThreadLocal 获取连接

    3.4 日志 TraceId¶

    日志框架通常使用：

    MDC

    内部也是：

    ThreadLocal<Map>

    保存：

    traceId
requestId
userId

    例如：

    2026-07-20
traceId=abc123
查询订单

    日志系统可以通过 traceId 串联整个请求链路。

    3.5 Locale 国际化上下文¶

    Spring：

    LocaleContextHolder

    保存：

    zh_CN
en_US

    用于：

    • 国际化提示
    • 日期格式
    • 金额格式

    4. 为什么异步会导致上下文丢失？¶

    同步：

    Thread-1

Request

 |
 SecurityContext

 |
 Transaction

 |
 TraceId

    没有问题。

    但是异步：

    CompletableFuture.runAsync(() -> {

    service.run();

});

    执行流程：

    请求线程 Thread-1

        |
        |
        | 提交任务
        |
        v

线程池


        |
        v


异步线程 Thread-2

        |
        |
        +-- service.run()

    此时：

    Thread-1

ThreadLocal

{
 user,
 traceId,
 transaction
}


Thread-2

ThreadLocal

{}

    因为：

    ThreadLocal 不会自动跨线程复制。

    5. 为什么需要上下文传播？¶

    异步任务虽然换了线程，但是业务上可能仍然属于同一个请求。

    例如：

    用户：

    张三

    提交订单。

    主线程：

    创建订单

    异步线程：

    发送邮件
发送短信
记录日志

    这些操作仍然需要：

    当前用户
TraceId
租户信息

    否则：

    用户=null

traceId=null

    导致：

    • 日志无法关联
    • 权限丢失
    • 多租户错误

    6. 什么叫“手动传递”？¶

    最简单方式：

    SecurityContext context =
    SecurityContextHolder.getContext();


executor.submit(() -> {

    SecurityContextHolder
        .setContext(context);


    doSomething();

});

    流程：

    Thread-1

获取上下文

      |
      v

传递给任务

      |
      v

Thread-2

恢复上下文

    缺点：

    • 代码重复
    • 容易遗漏
    • 维护困难

    7. 什么叫“各种包装”？¶

    包装的本质：

    给异步任务套一层，在执行前恢复上下文，执行后清理上下文。

    7.1 Runnable 包装¶

    原始：

    executor.submit(task);

    包装后：

    Runnable

     |
     v

ContextAwareRunnable

     |
     v

执行前:

恢复 ThreadLocal


执行后:

清理 ThreadLocal

    7.2 Spring Security 包装¶

    例如：

    DelegatingSecurityContextRunnable

    作用：

    捕获 SecurityContext

        |

异步线程恢复

        |

执行任务

    7.3 TaskDecorator¶

    Spring 在线程池中常用：

    executor.setTaskDecorator(...)

    效果：

    提交任务

      |
      v

自动复制上下文

      |
      v

线程池执行

    业务代码不用关心。

    7.4 上下文传播框架¶

    常见方案：

    • Alibaba TransmittableThreadLocal
    • Micrometer Context Propagation
    • OpenTelemetry Context

    它们解决：

    Thread-1

上下文

    |
    |
    v

Thread-2

恢复上下文

    8. 哪些 ThreadLocal 值适合传播？¶

    类型 是否推荐传播
    TraceId ✅ 推荐
    RequestId ✅ 推荐
    当前用户信息 ✅ 推荐
    租户ID ✅ 推荐
    Locale 可以
    Request对象 ⚠️ 谨慎
    Session ⚠️ 谨慎
    Transaction ❌ 通常不要
    数据库连接 ❌ 不允许

    9. 为什么事务一般不跨线程传播？¶

    例如：

    @Transactional
public void save(){

    CompletableFuture.runAsync(() -> {

        dao.save();

    });

}

    很多人认为：

    异步任务应该还在事务里面。

    实际上：

    Thread-1

事务

 |
 Connection


Thread-2

没有事务

 |
 新连接

    原因：

    事务绑定在线程。

    跨线程传播事务可能导致：

    • 数据库连接混乱
    • 提交时间不可控
    • 事务边界不明确

    10. 为什么 Spring 不自动复制所有 ThreadLocal？¶

    因为不是所有上下文都适合复制。

    例如：

    Request¶

    里面包含：

    Socket
输入流
输出流

    请求结束后可能已经失效。

    Transaction¶

    里面包含：

    数据库连接
事务状态

    跨线程非常危险。

    所以框架通常只传播明确安全的上下文。

    11. 核心总结¶

    Servlet 时代：

    请求 = 线程

    所以：

    ThreadLocal
      |
      v
保存上下文

    非常方便。

    但是现代应用：

    异步
线程池
CompletableFuture
消息队列
Reactive
微服务

    导致：

    请求生命周期

不等于

线程生命周期

    于是产生：

    线程切换

      |
      v

ThreadLocal丢失

      |
      v

上下文传播

    解决方式：

    1. 手动传递
    2. Runnable / Callable 包装
    3. TaskDecorator
    4. Context Propagation 框架

    一句话理解：

    ThreadLocal 解决的是“同一个线程内共享上下文”，而上下文传播解决的是“业务请求跨线程执行时如何保持上下文连续”。
