    AI Agent 是怎么"看懂"网页的：从 Accessibility Tree 说起¶

    当我们让 AI Agent 帮忙操作浏览器——点击按钮、填写表单、读取页面内容——第一个要回答的问题其实是：AI 看到的"页面"长什么样？ 是截图？是 HTML 源码？还是别的什么东西？

    答案是大部分情况下，AI 看到的既不是截图也不是 HTML，而是一棵叫做 Accessibility Tree（无障碍树） 的结构。这篇文章把这个概念拆开讲清楚。

    一、Accessibility Tree 是什么¶

    Accessibility Tree 不是某个框架的发明，而是浏览器原生就有的机制，最初为屏幕阅读器服务——让视障用户能"听"到页面内容。

    浏览器渲染页面时，内部其实维护了好几棵树：

    • DOM 树：HTML 的完整结构，包含所有元素，不管用户看没看到。
    • Render 树：经过 CSS 计算后，真正要画出来的部分。
    • Accessibility Tree：在 DOM 之上进一步精简，只保留用户能感知和交互的内容，每个节点带上角色（role）、名称（name）、状态（state）等语义信息。

    用一个类比：DOM 是建筑蓝图（包含每根管线），Accessibility Tree 是交房时的设备清单（只列你摸得到、用得着的东西）。

    二、从 DOM 到 Accessibility Tree：一个按钮的旅程¶

    假设 DOM 里有这样一个按钮：

    <button
  class="btn btn-primary ant-btn ant-btn-lg"
  id="create-dataset-btn"
  data-track="click_create_dataset"
  data-permission="admin"
  style="background: #2970ff; border-radius: 8px; margin-top: 12px;"
  disabled
  aria-label="新建知识库"
  aria-describedby="btn-hint"
  title="点击创建一个新的知识库"
  tabindex="0"
  onclick="handleCreate()"
>
  <svg class="icon"><use href="#icon-plus"/></svg>
  <span>新建知识库</span>
</button>

    经过浏览器构建 Accessibility Tree 之后，AI 看到的是：

    button "新建知识库"
  disabled: true
  description: "..."（aria-describedby 指向的内容）
  focusable: true

    就这么点东西。从一大段 HTML 精简成了一个角色、一个名字、几个状态。

    保留了什么¶

    信息 值 来源
    role button HTML 标签 <button> 自动映射
    name "新建知识库" 优先级：aria-label > 内部文本 > title
    description 补充说明文字 aria-describedby 指向的元素内容
    disabled true HTML disabled 属性
    focusable true 元素可被键盘聚焦

    除了 disabled，常见的状态还有：checked（复选框是否勾选）、expanded / collapsed（下拉菜单是否展开）、pressed（切换按钮是否按下）、selected（选项是否选中）、focused（当前是否获得焦点）。

    丢掉了什么¶

    信息 为什么丢
    class="btn btn-primary ant-btn" CSS 类名是实现细节，对用户无语义价值
    id="create-dataset-btn" DOM ID 是开发用的
    data-track、data-permission 自定义 data 属性全部丢弃
    style="background: #2970ff; ..." 视觉样式不进无障碍树
    onclick="handleCreate()" 事件处理器不暴露
    tabindex="0" 不直接保留，间接体现为 focusable: true
    <svg> 图标 图标如果不带 aria-label，在树里是透明的
    title 属性 已有 aria-label 时不再重复

    核心原则就一句话：对用户没有意义的信息，全部过滤。

    三、AI 为什么更喜欢 Accessibility Tree¶

    浏览器自动化领域有三种"看页面"的方式，对比一下就很清楚：

    方式一：原始 HTML¶

    把整个 DOM 源码丢给 AI。

    优点是信息最完整，CSS 类名、data 属性、嵌套结构全都在。缺点是token 爆炸——一个复杂页面的 HTML 轻松几万甚至十几万 token，其中大量是 div、span、class 名等噪音。AI 要从里面找到"新建知识库"按钮，得在一堆嵌套 div 里翻。而且很多 DOM 节点实际不可见（display: none），AI 无法区分。

    方式二：截图 + 视觉识别¶

    对页面截图，让多模态模型"看图找按钮"。

    优点是所见即所得，能处理 Canvas、WebGL 等无障碍树残缺的页面，也能分析颜色、布局等视觉信息。缺点是 token 消耗大（一张截图几千 token），坐标定位脆弱（窗口大小一变、页面一滚动就失效），而且识别精度依赖视觉模型的能力——小字、密集按钮、中文混英文这些场景容易出错。

    方式三：Accessibility Tree 快照¶

    提取页面的无障碍树，输出结构化文本。

    [button] "新建知识库" ref=e12
[button] "导入" ref=e13
[textbox] "搜索知识库..." ref=e14
[link] "首页" ref=e15
[checkbox] "仅显示我的" ref=e16  checked

    Token 消耗极低（同样的页面，无障碍树可能只有 HTML 的 1/10），自动过滤不可见元素，每个元素有稳定的 ref 标识。AI 只需要说"点击 ref=e12"，不需要关心它在页面哪个像素位置。

    维度 HTML 截图 Accessibility Tree
    Token 消耗 极高 高 低
    元素定位精度 中（需解析 DOM） 低（坐标易失效） 高（ref 稳定）
    可见性过滤 无 天然可见 自动过滤
    Canvas/WebGL 完整 能处理 失效
    视觉信息 有 CSS 完整 无
    适合场景 调试/底层分析 视觉验证/兜底 日常操作（默认方案）

    实际最佳实践是默认用 Accessibility Tree 定位和操作元素，只在需要分析视觉样式或遇到 Canvas 等特殊页面时才辅以截图，HTML 基本不直接丢给 AI。

    四、主流浏览器 Skill 与 Accessibility Tree¶

    目前生态里几个主流的浏览器自动化 Skill，底层都不同程度地依赖 Accessibility Tree。

    Midscene Skills（字节 web-infra-dev）¶

    安装：npx skills add web-infra-dev/midscene-skills@browser-automation -g -y

    核心卖点是用自然语言驱动浏览器操作，底层基于 Playwright。Playwright 原生提供 page.accessibility.snapshot() API，Midscene 正是通过这个 API 获取页面结构，再结合 AI 语义理解来匹配用户指令和页面元素。你说"点击新建知识库按钮"，AI 在无障碍树里找到 button "新建知识库"，然后通过 ref 定位点击。

    腾讯 BrowserSkill¶

    架构比较独特：浏览器扩展 + CDP（Chrome DevTools Protocol）+ 本地 WebSocket 桥接。最大特点是复用用户已有的登录态——创建一个隔离的"Agent Window"，共享你的浏览器 profile，所以操作需要认证的内部系统特别方便。

    底层走 CDP 通道，CDP 提供了 Accessibility.getFullAXTree() 等接口来获取无障碍树。BrowserSkill 的浏览器扩展在页面内提取无障碍信息，传给 AI 做决策。纯本地桥接，数据不出本机。

    Browserbase Skills（Claude Code 生态）¶

    为 Claude Code 设计的浏览器自动化插件。同样基于 Playwright，通过 Accessibility Tree 快照作为 AI 理解页面的主要方式，辅以截图做视觉验证。

    Playwright MCP / agent-browser¶

    Playwright MCP 是微软的 Model Context Protocol 服务器，明确推荐默认使用 Snapshot 模式（即 Accessibility Tree），只在需要分析视觉或底层实现时才切换到截图或 HTML。agent-browser 也是类似思路，通过 CDP 获取无障碍树作为 AI 的"眼睛"。

    共同点¶

    这些工具不约而同选择了 Accessibility Tree 作为默认方案，原因很简单：它是浏览器帮你做好的"页面语义摘要"，质量高、token 省、定位准。AI 拿到的不是原始数据，而是经过浏览器"理解"和"过滤"后的结构化信息。

    五、Accessibility Tree 的局限¶

    Accessibility Tree 不是万能的，有几个需要注意的场景：

    前端语义化不足时，树会"缺斤少两"。 如果开发者大量使用 <div onclick="..."> 模拟按钮而没加 role 和 aria-label，这些元素在无障碍树里会消失或信息不全。

    <!-- 反面教材：无障碍树里完全消失 -->
<div class="icon-btn" onclick="handleCreate()">
  <svg>...</svg>
</div>

<!-- 好一些：有角色但没名字 -->
<div role="button" onclick="handleCreate()">
  <svg>...</svg>
</div>

<!-- 正确写法：无障碍树里完整呈现 -->
<div role="button" aria-label="新建知识库" onclick="handleCreate()">
  <svg>...</svg>
</div>

    Canvas / WebGL / 自定义画布 这类页面，无障碍树基本是空的——画布里的内容对浏览器来说就是一个 <canvas> 元素，里面的图形、按钮全部不可见。这种情况只能靠截图 + 视觉识别来兜底。比如你们 Dify 的工作流编辑器画布区域，节点拖拽和连线操作在无障碍树里可能就不够完整。

    动态内容 有时滞。SPA 页面里通过 JS 动态插入的内容，无障碍树会更新，但如果 AI 在更新完成之前就取了快照，可能拿到的是旧数据。

    六、如何查看当前页面的 Accessibility Tree¶

    你现在就可以试：

    Chrome DevTools 方式： 打开 Chrome → F12 → 在 Elements 面板底部找到 "Accessibility" 标签页，选中任意元素就能看到它在无障碍树中的位置和属性。

    Playwright API 方式：

    from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://a6.inewgrand.com")

    # 获取完整的 accessibility tree
    snapshot = page.accessibility.snapshot()

    import json
    print(json.dumps(snapshot, indent=2, ensure_ascii=False))
    # 输出类似：
    # {
    #   "role": "WebArea",
    #   "name": "Dify 控制台",
    #   "children": [
    #     {"role": "button", "name": "新建知识库"},
    #     {"role": "textbox", "name": "搜索..."},
    #     ...
    #   ]
    # }

    小结¶

    Accessibility Tree 是浏览器为每个页面自动生成的一份"用户可感知元素清单"。它过滤掉了 DOM 中的实现噪音，只保留角色、名称、状态等语义信息。AI Agent 浏览器自动化领域几乎都选择了它作为默认方案——token 省、定位准、天然过滤不可见元素。但它不是万能的，前端语义化不足或 Canvas 场景下会力不从心，这时需要截图识别来兜底。

    下次当你让 AI 操作浏览器时，不妨想想：它"看到"的不是你眼前的画面，而是一棵精简过的语义树。理解这一点，有助于你写出更好的自动化指令，也有助于你理解为什么某些页面 AI 能轻松操作，而某些页面它总是"找不到按钮"。
